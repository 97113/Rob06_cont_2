# RS06 電動ブレーキアクチュエータ制御器

M5Stack Core2 + Module13.2 PwrCAN + RobStride RS06

---

## 1. 配線（電源投入前に必ず確認）

> ⚠ **PwrCAN の XT30(2+2) 電源ピンは DCジャック(9〜24V)に降圧なしで直結**されています。
> RS06 の XT30 には **48V** が乗っています。両者を XT30 同士で接続すると PwrCAN が破壊されます。

| 接続 | 内容 |
|---|---|
| CAN 信号 | RS06 の CANH/CANL **のみ** を PwrCAN の CAN 端子へ。電源ピンは結線しない |
| PwrCAN 給電 | DCジャック（5.5/2.1mm、センタープラス）に **9〜24V** を別系統で供給 |
| モータ給電 | 13S Li-ion から RS06 へ直接（Core2/PwrCAN とは完全分離） |
| DIP（CAN ピン） | **CH3 と CH6 のみ ON**（下表）。RS485 Select 側に同じピンを割り当てないこと |
| DIP（終端） | PwrCAN 側 120Ω を ON。バス両端で計 2 本 |

終端の確認：全電源 OFF で CANH–CANL 間が **約 60Ω** なら正常（120Ω が 2 本並列）。

### PwrCAN「CAN Select」DIP → Core2 GPIO

基板シルクの PIN MAP と Core2 の M5-Bus ピン番号を突き合わせた確定表です。

| DIP | 方向 | Core2 GPIO | M5-Bus | 備考 |
|---|---|---|---|---|
| CH1 | CAN TX | G14 | 16 | |
| CH2 | CAN TX | G2 | 23 | ストラップピン |
| **CH3** | CAN **TX** | **G27** | 21 | **本機の実配線・既定** |
| CH4 | CAN TX | G0 | 24 | ストラップピン・非推奨 |
| CH5 | CAN RX | G13 | 15 | |
| **CH6** | CAN **RX** | **G19** | 22 | **本機の実配線・既定** |
| CH7 | CAN RX | G34 | 26 | 入力専用 |
| CH8 | CAN RX | G35 | 2 | 入力専用 |

CH1〜4 が TX 側、CH5〜8 が RX 側です（G34/G35 が入力専用で RX 側にしか現れないことと整合）。
**各グループから1つずつだけ ON** にしてください。

> ⚠ **基板シルクの読み間違いに注意。** PwrCAN の PIN MAP は `Core / Core2 / CoreS3` の
> 3列が並んでおり、**CoreS3 列には Core2 に存在しないピン（G10, G6, G7 など）が入っています**。
> 特に CH8 の行は `G35 / G35 / G10` で、右端の G10 を拾ってしまいがちです。
> ESP32 の **GPIO6〜11 は内蔵SPIフラッシュ専用**で M5-Bus にも出ていないため、
> Core2 で G10 は絶対に有り得ません。必ず **真ん中の Core2 列**を読んでください。

### CAN が繋がらないとき — 自動スキャン

**BtnA（左のタッチパッド）を押しながら電源を入れる**と CAN スキャナが起動します。
DIP の全ピン組み合わせ（4×4）× ボーレート（1M/500K/250K/125K）× モータ CAN_ID（0x00〜0x7F）を
掃引し、応答した組み合わせを NVS に保存してそのまま起動します。

判定は3種類出ます。

| 表示 | 意味 | 次にやること |
|---|---|---|
| `FOUND id 0xXX TX Gxx RX Gxx` | モータが応答。設定を保存済み | そのまま使用可。表示された DIP 番号と実物が一致しているか確認 |
| `ACK only` | バス上の誰かが ACK を返すがモータ ID が応答しない | ピンとボーレートは正しい。モータ ID が想定外か、別ノードがいる |
| `no CAN response` | どのピンでも ACK が無い | 下の一覧を確認 |

`no CAN response` の場合の典型原因（可能性の高い順）：

1. **CANH / CANL の入れ替わり** — 極性が逆だと一切通信しません
2. **モータ電源(48V)が入っていない** — トランシーバが動かず ACK を返せません
3. **終端抵抗** — 2本無い / 1本しか無い
4. **PwrCAN 自身の給電** — DCジャックに 9〜24V が来ているか（M5 本体は USB で動くので気付きにくい）
5. **RS485 Select DIP が CAN と同じピンを掴んでいる** — マニュアル明記の禁止事項
6. **DIP が複数 ON / 全部 OFF**

スキャン結果は CONFIG ページ最下段にも常時表示されます（`CAN TX Gxx / RX Gxx / 1000k / id 0x7F >`）。

### CAN SETUP ページ（配線・ボーレート・ID を実機で切り替える）

CONFIG ページ最下段の CAN 情報行を**タップ**すると CAN SETUP が開きます（停止中のみ操作可）。
**書き込み直しなしで** TX/RX ピン、ボーレート、モータ ID を切り替えられます。

```
              CAN SETUP
 TX pin     [<]  G27 (CH3)  [>]
 RX pin     [<]  G19 (CH6)  [>]
 bit rate   [<]  1000 k     [>]
 motor id [-16][-1] 0x7F [+1][+16]

 [ APPLY (restart CAN) ] [ WRITE ID TO MOTOR ]
              [ CLOSE ]
```

| ボタン | 動作 | 影響範囲 |
|---|---|---|
| **APPLY** | 設定を NVS に保存し、**TWAI ドライバを停止→新しいピン/ボーレートで再起動**。フォルトもクリア | Core2 のみ。モータには触れない |
| **WRITE ID TO MOTOR** | **Type7** でモータ自身の CAN_ID を書き換え、続けて **Type22** で不揮発保存 | モータの設定が恒久的に変わる |

TX/RX の選択肢は DIP の CH 番号付きで表示されるので、**実物の DIP と画面を突き合わせる**だけで済みます。
MONITOR ページの診断行（`st: TX RX MS TEC BE Q`）を見ながら APPLY を繰り返せば、
どの組み合わせで送受信が動き出すかが直接わかります。

`WRITE TO MOTOR` は **バス上にモータが1台だけの状態で**実行してください。
同じ ID のモータが複数いると、どれが書き換わるか不定になります。

Type7 のフレーム構造（`rs06_driver.cpp` の `setCanId()`）：

```
29bit ID : bit28-24 = 0x07
           bit23-16 = 新しい CAN_ID     ← ここ
           bit15-8  = ホスト ID (0xFD)
           bit7-0   = 現在のモータ CAN_ID
Data     : 00 x8
応答      : Type0（ブロードキャストフレーム）
```

ID が分からなくなった場合は BtnA 起動のスキャナが 0x00〜0x7F を掃引して見つけます。

起動時の既定値は `Params`（[`src/types.h`](src/types.h)）の `can_tx` / `can_rx` / `can_baud` で、
現在は実機に合わせて **TX G27 / RX G19 / 1Mbps** です。ただし**実際に使われるのは NVS の保存値**なので、
既定値を変えただけでは古い設定が生き残ります。

そのため `Params` には `magic`（[`src/config.h`](src/config.h) の `PARAMS_MAGIC`）を持たせてあり、
**既定値やレイアウトを変えたら `PARAMS_MAGIC` を1つ進める**と、NVS の古いブロブが破棄されて
新しい既定値が確実に効きます。

**コギング補正** はメーカー製 PC 上位機ソフトでのみ校正できます。使う場合は `iq_test=1` → 再起動 → PC で校正 → `alveolous_open=1` を事前に実施してください。本ファームは校正済みかどうかに関与しません。

## 2. 書き込み

### 依存ライブラリ

**外部ライブラリは `M5Unified` の 1 つだけ**です。`SD.h` / `SPI.h` / `Preferences.h` /
`driver/twai.h` / `esp_timer.h` / `esp_heap_caps.h` / `freertos/*` はすべて
ESP32 ボードパッケージに同梱されているので、個別のインストールは要りません。

| | ESP32 core | M5Unified | M5GFX |
|---|---|---|---|
| 開発時の検証バージョン | 3.3.7 | 0.2.15 | 0.2.21 |

**PlatformIO は自動で取得します**（`platformio.ini` に宣言済み）。手当が要るのは Arduino IDE だけです。

> `fatal error: M5Unified.h: No such file or directory` はこのライブラリ未導入が原因です。
> 下の手順1でインストールしてください。

### 方法A: Arduino IDE

1. **ツール → ライブラリを管理…**（`Ctrl+Shift+I`）で **`M5Unified`** を検索し、
   M5Stack 製のものをインストール。依存ライブラリを聞かれたら **Install all**
   （描画層の `M5GFX` が一緒に入ります。必須です）
2. `Rob06_cont_2.ino` をダブルクリックして Arduino IDE で開く
   （`.ino` は空ファイル。Arduino はスケッチ直下の `src/` を再帰的にコンパイルするため、
   実体は `src/main.cpp` の `setup()` / `loop()` です。
   スケッチフォルダ名と `.ino` の名前は一致している必要があります）
3. Core2 を USB-C で接続
4. **ツール → ボード → M5Stack → M5Core2**
5. **ツール → PSRAM → Enabled**（30秒ログリングが PSRAM 上にあるため必須。
   無効だと 2000 サンプルの縮退リングに落ちます）
6. **ツール → Upload Speed → 921600**（失敗するなら 115200 に落とす）
7. **ツール → シリアルポート** で Core2 の COM を選択
8. → ボタン（Upload）

### 方法B: PlatformIO

```bash
pip install platformio
pio run -t upload
```

espressif32@^6.9.0 / arduino framework。`.ino` は無視されます。
M5Unified は `lib_deps` から自動で取得されるので、ライブラリの手動導入は不要です。

### USBドライバ

COMポートが現れない場合はドライバを入れてください。
- Core2 v1.1（現行）: **CH9102F** → WCH の CH343SER ドライバ
- Core2 v1.0: **CP2104** → Silicon Labs CP210x VCP ドライバ

### 書き込みに失敗するとき

Core2 は自動リセットで書き込みモードに入りますが、失敗する場合は
**電源ボタン（左側面）を 6 秒長押しで完全 OFF → 押し直して ON** してから再試行、
それでも駄目なら Upload Speed を 115200 に下げてください。

## 3. アーキテクチャ

```
core 1  制御タスク 1 kHz  (controller.cpp)
        Type1 送信 → Type2 受信（角度/角速度/トルク/温度）
        Type17(VBUS 200Hz・制動中500Hz / iqf 50Hz) と Type21(50Hz) は
        「投げっぱなし＋届いたら拾う」方式
core 0  UI 20 Hz (ui.cpp) + SD ダンプ
```

### 受信モデル（重要）

モータからのフレームは `Rs06::pump()` が一箇所で受け取り、**通信タイプで仕分けます**。
「待っていたものと違うから捨てる」ことは一切しません。

| タイプ | 行き先 |
|---|---|
| Type2 | 最新フィードバック |
| Type17 | index をキーにしたパラメータキャッシュ |
| Type21 | フォルト／警告ワード |

これは実測で判明した障害への対処です。**補助読み出し(Type17)の応答は、要求したスロットが
終わった後に届くのが普通**でした。旧実装はスロット内で 300 µs だけ待ち、間に合わなかった応答を
次スロットの Type2 待ちが取り出して捨てていたため、一度でも 1 スロット遅れると二度と回復しません。
その結果、**VBUS は設計 200 Hz に対し実測 0.7 Hz、電流に至っては一度も更新されず**、
VBUS を根拠とする保護がすべて目隠しで動いていました（`tools/` の全キャプチャで確認）。

現在は `requestParam()` / `requestFault()` が要求を投げるだけで待たず、
`paramValue()` / `faultWords()` が**経過時間つき**で読み出します。
`AUX_STALE_MS`(100ms) より古い値は安全層が使いません。

**運動制御モード（mode 0）一本化。** 実行時にモードレジスタ 0x7005 を書き換えないため、
マニュアルの「走行中のモード切替禁止」制約に触れません。

```
t_ref = Kd·(v_set − v_act) + Kp·(p_set − p_act) + t_ff

位置制御  : 台形軌道の (p_set, v_set) + t_ff = Ĵ·a + Fc·sign(v) + Fv·v
トルク制御: Kp=0、Kd=微小、t_ff = 指令トルク
```

`Type24` アクティブ報告は **OFF のまま**です（最小 10ms で粗く、Type1 の応答で 1kHz が取れるため）。

## 4. プロトコル実装上の注意（実装済み・変更時は要注意）

**エンディアンが混在しています。**

| フレーム | バイトオーダ |
|---|---|
| Type1 / Type2 の 8 バイトペイロード | **ビッグエンディアン** |
| Type17 / Type18 の index と Byte4-7 | **リトルエンディアン** |

マニュアルの `loc_kp` 読み出し例（応答 `1E 70 00 00 00 00 F0 41` = 0x41F00000 = 30.0）で検証済み。

その他：

- **Type1 のトルク指令は ID の bit23〜8 に入ります**（ペイロードではない）
- **Type2 に電流は無い** → `iqf`(0x701A) を Type17 で取得
- **Type2 に過電圧フォルトは無い** → Type21 の bit3 のみ。`readFault()` で取得
- **位置フィードバックは ±4π で周回** → `controller.cpp` でアンラップ。ただし Type1 の
  `p_set` も ±4π が上限なので、**動作範囲は機械ゼロから ±4π 以内**に収める必要がある。
  逸脱は軽度異常（`EV_POS_LIMIT`）として検出

## 5. 安全

| 層 | 実装 |
|---|---|
| モータ自律 | `canTimeout`(0x7028) = 2000（**100ms**）。Core2 がハングしてもモータが自律停止 |
| 熱ディレート | `temp_derate`(既定100℃) から線形減トルク、`temp_trip`(既定130℃) で重度停止 |
| 回生予防 | 制動中は `P = τ·ω` を評価し、`regen_w_max` を超えないようトルク上限と**軌道の減速度上限**を同時に絞る（1kHz、遅延ゼロ） |
| 回生検知 | VBUS 監視。閾値は **min(58V, 静止時VBUS + margin)**。静止時 VBUS は**モータ非励磁中の 9 サンプルの中央値**で確定（1サンプルだけを一生使い続けない）。超過で制動トルク即カット |
| 低電圧 | **max(`vbus_min`, 静止時VBUS × 0.70)**。固定値と電源相対値の高い方を使うので、32V ベンチ電源でも 13S パックでも設定変更なしで守れる（実測最大サグは約11%で十分な余裕） |
| 鮮度判定 | VBUS が `AUX_STALE_MS` より古ければ上記の判定は**行わない**（古い値で制動を切る方が危険）。画面には `AUX-QUIET`、電圧値には `?` が付く |
| 過電圧確定 | Type21 bit3 → 重度停止 |
| 軽度異常 | 指令ソース失調 / CAN 連続欠落5回 / 低電圧警告 / 位置逸脱 → 40ms でトルクをランプダウンし Kd のみのダンパ停止 → IDLE |
| 重度異常 | 過電流・過温・エンコーダ異常・ストール・過電圧・低電圧・CAN 連続欠落50回・バスオフ → 即 Type4 励磁OFF |
| 原因表示 | Type21 の各ビットは**個別のイベント**に対応。以前は駆動IC異常・位置初期化異常・ハードID異常・過温をまとめて "OVERCURRENT" と表示していた |
| 常時 | **BtnC = 停止**（全ページ有効。キャリブ中は ABORT） |

### イベントは2語ある

| 語 | 意味 | クリア条件 |
|---|---|---|
| `events` | **ラッチ**。何が起きたか | CLEAR FAULT / START |
| `active` | **瞬時**。いま何が効いているか | 毎tick再構築（自動） |

分離した理由は実測です。`EV_REGEN_LIMIT` は速い移動のたびに必ず一瞬立ちます
（600W ÷ 31.5rad/s = 19.05Nm で、トルク上限 20Nm をわずかに下回るため）。
旧実装は両者を同じ語に入れて消さなかったので、**12本のキャプチャ中10本で
"REGEN-LIM" が点灯しっぱなし**になり、本物の異常を隠していました。

画面右上とGUIの表示は、ラッチがあればそれを、無ければ瞬時側を `~` 付きで出します
（`~REGEN-LIM` = 「いま回生制限中」、`REGEN-LIM` = 「異常が発生した」ではない）。

## 6. 操作

**BtnA = ページ送り / BtnB = START・MOVE / BtnC = STOP**

| ページ | 内容 |
|---|---|
| MONITOR | トルク・電流・指示角度・角度・モータ温度 ＋ 角度トレンド |
| CONTROL | POSITION/TORQUE 切替、目標値ステッパ（値タップでテンキー）、ゼロリセット（機械/ソフト）、フォルトクリア |
| CONFIG | ゲイン・リミッタ・同定値の編集、CALIB 実行、SD DUMP |

数値入力は `[--][-][+][++]`、値をタップするとテンキーが開き **OK を押すまで反映されません**。

ゼロ点は 2 段構成：
- **ZERO (motor)** … Type6 で機械ゼロを書き換え（**停止中のみ**）
- **ZERO (soft)** … Core2 の NVS にオフセットを保持（何度でもやり直せる）

## 6.5 PC からの制御と波形観測（USB）

Core2 は USB で **921600 baud の行指向プロトコル**を話します。付属の GUI で操作と波形観測ができます。

**`rs06_console.bat` をダブルクリック**で起動します（プロジェクト直下）。

コマンドラインから起動する場合、**シェルによって書き方が違います**。

| シェル | コマンド |
|---|---|
| **PowerShell** | `.\rs06_console.bat COM3`  ← **`.\` が必須** |
| コマンドプロンプト (cmd) | `rs06_console.bat COM3` |

PowerShell はセキュリティ上、カレントディレクトリのコマンドを PATH から探しません。
`.\` を付けずに実行すると `用語 'rs06_console.bat' は ... 認識されません` になります
（バッチ側の問題ではありません）。

| 引数 | 動作 |
|---|---|
| なし | GUI を開き、ポートは画面で選択 |
| `COM3` 等 | 起動時にそのポートへ接続 |
| `--selftest` | **GUI を開かず**に Python・依存ライブラリ・検出できる COM ポートを表示して終了 |

バッチは自分の置かれたフォルダへ `cd` してから実行するので、どこから起動しても
`tools\` と `logs\` のパスが正しく解決されます。`python` が PATH に無ければ `py -3` を試し、
どちらも無ければインストール手順を表示します。異常終了時は原因を表示して `pause` するので、
ダブルクリック起動でもエラーが読めます。

直接起動する場合は従来通りこちらでも動きます。

```bash
python tools/rs06_console.py
```

ポートを選んで Connect すると、100 Hz のテレメトリ配信が始まります。

| 画面 | 内容 |
|---|---|
| 左ペイン | START / STOP / CLEAR FAULT、モード切替、角度 MOVE、トルク指令、ゼロリセット、CALIBRATE |
| 右ペイン | **ライブ波形（直近20秒）** — 指示角度 vs 実角度 / 指示トルク vs 実トルク / 電流と速度 |
| 下部 | 送受信ログ。異常時は `UNDERVOLT` のように**イベント名がデコード**されて表示されます |

### CSV 保存（3通り）

| 方法 | 内容 | 出力先 |
|---|---|---|
| **REC start / stop** | ライブ配信（100Hz）を受信しながら**逐次 CSV に追記**。長時間の記録向け | 保存ダイアログで指定 |
| **save buffer as CSV** | 画面に出ている直近20秒のバッファをそのまま書き出す | 保存ダイアログで指定 |
| **CAPTURE + PLOT** | 1kHz キャプチャ。**自動で `tools/logs/capture_<日時>.csv` に保存**され、解析ウィンドウの `Save CSV as...` で別名保存も可能 | 自動 ＋ 任意 |

### CSV の読み込み

`Load CSV...` で保存済みファイルを読み戻し、**キャプチャと同じ解析ウィンドウ**で開けます。

ヘッダから形式を自動判別するので、どの保存方法で作ったファイルでもそのまま開けます。

| ヘッダの時刻列 | 想定元 |
|---|---|
| `t_us` | 1kHz キャプチャ / microSD ダンプ |
| `t_s` | save buffer as CSV |
| `t_ms` | REC（ライブ記録） |

列名は `p_cmd_deg` → `p_cmd` のように別名解決され、足りない列はゼロ埋めして
**読める分だけ描画**します。時刻列が見つからないファイルは理由付きで拒否します。
読み込み時にサンプル数・実サンプリング周波数・欠落列がウィンドウ上部に表示されます。

`Save CSV as...` は**元ファイルのヘッダと行をそのまま保存**するので、
読み込み→再保存で内容が変わることはありません。

### 1 kHz キャプチャと解析ウィンドウ

ライブ配信は 100 Hz なので、**100ms の応答を評価するには粗すぎます**。
`CAPTURE + PLOT` を押すと、ファームウェア内の **PSRAM リング（1 kHz、実データ）** から直近 N 秒を
吸い出し、**対話的な解析ウィンドウ**を開きます（画像ではなくライブのグラフです）。

**拡大・縮小・目盛り**

| 操作 | 動作 |
|---|---|
| ホイール | **X軸ズーム**（カーソル位置中心） |
| Shift + ホイール | **Y軸ズーム**（そのサブプロットのみ） |
| `X +` / `X -` / `Y +` / `Y -` | ボタンでの拡大・縮小 |
| **`auto Y`** | **表示中のX範囲だけを見てY軸を自動再設定**。拡大した細部が潰れなくなる |
| `auto XY` | 全体表示に戻す |
| 標準ツールバー | 範囲指定ズーム、パン、Home、画像保存 |

**カーソルと数値読み取り**

| 操作 | 動作 |
|---|---|
| **左クリック** | カーソル **A** を配置 |
| **右クリック** | カーソル **B** を配置 |
| `labels` チェック | 引き出し線ラベルの表示切替 |
| `clear cursors` | カーソル解除 |

カーソルを置くと、**その時刻の各信号の実測値が引き出し線付きのラベル**で該当サンプル上に表示され、
サンプル位置には点が打たれます。どの曲線の数値かが一目で分かります。

下部の表には全8信号について **A の値 / B の値 / B−A の差** が並び、
その上の行に **A と B の時刻、時間差 dt [ms]、および 1/dt の周波数換算**が出ます。

角度プロットには **最後の指令移動の開始時刻（灰）** と **±5deg 帯への初到達時刻（緑）** が
自動で入り、その所要時間がウィンドウ上部に表示されます。

ライブ側のグラフも同じ操作系です（カーソルを置くと自動スクロールが止まり、
その区間をじっくり見られます。`clear cursors` で追従に戻ります）。

3秒分で約 200 kB を送るため転送に 2〜3 秒かかり、その間 UI が固まります。
制御ループ自体は core1 で走り続けるので動作には影響しません。

### プロトコル（端末から直接叩く場合）

`serial_link.h` に全仕様があります。素の Tera Term などからでも操作できます。

```
PING / ID
START / STOP / CLEARFAULT
MODE POS | MODE TRQ
MOVE <deg>
TRQ <Nm>
ZERO MOTOR | ZERO SOFT
CALIB START | CALIB ABORT
PARAMS                  全パラメータを P <key>=<値> で返す
SET <key> <value>       kp kd kdt tlim thold db vlim alim dlim pmin pmax
                        jhat fc fv kt tder ttrip vmarg vmin regen
STREAM <hz>             0 で停止、上限 200
DUMP [秒]               1 kHz リングを CSV で吐く（既定 3 秒）
SDDUMP                  同じものを microSD へ
```

**シリアル経由のコマンドもすべて `ctrl::request()` を通ります。** タッチ画面と同じ状態機械・
同じリミッタ連鎖・同じ安全判定が適用されるので、PC から安全機構を迂回することはできません。

| 段 | 内容 | 得られる値 |
|---|---|---|
| 1 | 静定 | — |
| 2 | 速度掃引 ±0.5/1/2/4 rad/s | `fric_c`, `fric_v`（最小二乗） |
| 3 | トルクパルス 4N·m×60ms 正逆 | `j_hat` |
| 4 | 全力 200deg 移動 | `meas_vmax`, `meas_amax`, `meas_reach_ms`, `meas_vbus_sag` |
| 5 | 30deg ステップ × Kp{15,30,60,120} × Kd{0.5,1,2,4} | `kp`, `kd`（整定時間＋オーバーシュート最小） |

所要 約 25 秒。完了で NVS に保存し、結果画面に **200deg 到達時間と PASS/OVER 100ms の判定**を表示します。

**実行前に軸の可動範囲を空けてください。** 段 4 は全力移動、段 3 は開放トルクパルスです。

## 8. 性能についての注記

要求は「無負荷で 200deg を 100ms で初到達」ですが、**48V 運用ではこれは電圧律速で未達になる見込み**です。

- 200deg = 3.4907 rad を 100ms → 平均 34.9 rad/s、**巡航に 50 rad/s が必須**
- 必要トルクは約 10 N·m（ピーク 36 N·m に対し余裕あり）→ **律速はトルクではなく速度**
- 48V の無負荷速度は 480rpm ≒ 50.3 rad/s ＝ プロトコル上限そのもの。実負荷では届かない
- 実力は **130〜160ms 付近**と見込まれる（13S 満充電 54.6V ではやや改善）

このため制御側は「48V で出せる最速」を追求する構成にしてあり、
**キャリブレーション段 4 が実測値と要求値の乖離を数値で出します**。
仕様を満たす必要が生じた場合、選択肢は昇圧・ギヤ比変更・動作角の見直しのいずれかです。

```bash
test/host/run.sh
```

| テスト | 内容 |
|---|---|
| `test_rs06_driver` | スロットより遅い応答の回収、index ごとの仕分け、鮮度、キュー内の古いフレームで待ちが誤成立しないこと |
